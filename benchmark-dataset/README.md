# DevSecOps Java Benchmark — pilot v1

**Назначение:** небольшой воспроизводимый обучающий датасет для дипломного сравнения Semgrep, локальной LLM и совместного анализатора.

- **20 отдельных Java-файлов:** 10 примеров с заранее заданной проблемой и 10 контрольных примеров для этих категорий.
- **10 категорий:** SQL injection, command injection, path traversal, hardcoded credential, predictable token, sensitive logging, XXE, untrusted deserialization, HTML injection, SSRF.
- Файлы не содержат `main()` и **не предназначены для запуска**. Все секреты синтетические, адрес `example.invalid` зарезервирован для примеров.
- Названия `Case001.java` ... `Case020.java` специально не указывают правильный ответ. Разметка хранится отдельно в `ground_truth.json`.

## Установка рядом с Java-проектом

Распакуйте **папку `benchmark-dataset` целиком** в корень `code-security-analyzer` (рядом с `pom.xml`). Не переносите эти Java-файлы в `src/main/java` или `src/test/java`.

## Проверка Semgrep

Из корня Java-проекта (PowerShell):

```powershell
.\.venv-semgrep\Scripts\semgrep.exe scan --config p/default --metrics off --no-git-ignore --json --output semgrep-benchmark.json benchmark-dataset/java
python .\benchmark-dataset\evaluate_semgrep.py --report .\semgrep-benchmark.json
```

Обязательны доступ к Registry для `p/default`, наличие всех 20 файлов в `paths.scanned` и отсутствие ошибок Semgrep. Если инструмент выводит ошибку сканирования, не используйте результаты для расчётов.

## Проверка в JavaFX

Выберите корневую папку `code-security-analyzer`, оставьте выбранными **только 20 файлов в `benchmark-dataset/java`**, используйте `qwen2.5-coder:7b`. Не загружайте `ground_truth.json` в контекст LLM и не используйте её для подсказок модели. Сохраните результаты каждого анализа и точные версии инструментов.

Не нажимайте «Исправить весь проект» во время эксперимента: изменение исходных кейсов нарушит сопоставимость. Не запускайте код из набора.

## Как понимать метрики

`evaluate_semgrep.py` считает **грубую классификацию на уровне файлов**: срабатывание хотя бы одного правила для файла делает прогноз `vulnerable`. Для одной категории на один файл:

- TP — положительный файл, где была хотя бы одна находка;
- FN — положительный файл, где находок не было;
- FP — контрольный файл, где было хотя бы одно срабатывание;
- TN — контрольный файл без срабатываний.

**Ограничение:** одна посторонняя находка на положительном файле может дать TP, даже если целевая уязвимость не распознана. Поэтому для научной оценки нужны также ручная проверка совпадения CWE и локализации, разметка отдельных находок и дополнительный датасет большего размера. Этот набор — пилот для отладки методики, а не доказательство превосходства LLM.

## Контроль воспроизводимости

Сохраните дату, модели, температуру/seed (если поддерживается), версии Semgrep/Ollama, конфиг правил, число файлов, ошибок, длительность запуска. Проведите несколько повторов LLM и сравнивайте при идентичных входных файлах.

Исходники и манифест синхронизированы SHA-256 по каждому файлу. Скрипт проверит, что ни один кейс не изменён.
