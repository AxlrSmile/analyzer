# Security policy / Обращение с исходным кодом

Этот репозиторий — **исследовательский прототип**, а не сертифицированный анализатор безопасности. Ни Semgrep без срабатываний, ни вывод LLM, ни `Java PASSED` не гарантируют отсутствия уязвимостей.

## Модель угроз

- Доверенные элементы: установленный JDK 21, локальный исполняемый Semgrep, приложение и его правила, рабочая станция разработчика. Пути из `PATH` и переопределение `analyzer.semgrep.executable` должны задаваться **только доверенным пользователем**.
- Недоверенные элементы: анализируемые исходники, комментарии, внешние файлы, LLM-ответы и предложения исправлений. Текст этих элементов нельзя трактовать как системные инструкции.
- Java-валидация: `javac` в отдельной временной папке, с `-proc:none`, пустым classpath/sourcepath, лимитом времени. Это **не** контейнер или системная песочница.
- Статические инструменты и LLM не выполняют предложенный Java-код автоматически. Вручную запускать образцы только на синтетических данных и в контролируемой среде.
- Экспорт исправления разрешён только в **новый** файл. Приложение не перезаписывает существующие файлы и исходники. Экспортированный результат проверяет человек.

## CI

GitHub Actions запускает `mvnw clean test` и Semgrep по `src/main/java`; учебные уязвимые benchmark-файлы исключены из production SAST. Сканер сохраняет JSON/SARIF, и ошибка сканирования не превращается в «чистый» результат. По умолчанию находки report-only (`SEMGREP_FAIL_ON=none`). Включение блокирующего gate и публикации SARIF — отдельные решения владельца репозитория.

На 12.11.2026 в CI для коммита `95d8a14` есть **2 срабатывания ProcessBuilder / ERROR**, оба нуждаются в подтверждении: [docs/SECURITY-TRIAGE-9.0-RU.md](docs/SECURITY-TRIAGE-9.0-RU.md). **Не** добавляйте исключения `nosemgrep` только ради зелёного CI.

## Конфиденциальность

- Используйте локальный Ollama и убедитесь, что выбранный endpoint не отправляет исходники в сторонние сервисы.
- Не помещайте токены, пароли, приватные ключи, реальные персональные данные или коммерческие секреты в benchmark и публичный репозиторий.
- Проверяйте `git diff --cached`, `git ls-files`, экспортные CSV/MD и артефакты перед публикацией; отчёты могут содержать пользовательские заметки и фрагменты кода.
- Если обнаружили новую проблему, сообщите владельцу проекта без публикации чужих секретов или эксплуатируемых данных. Не прикладывайте реальные атакующие данные из сторонних систем.
